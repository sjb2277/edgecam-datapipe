## 문제 → 가설 → 검증 → 결론
1. 문제: 클립 모드 최대 지연 61.4ms (평균 5.2ms)
   - 가설 A: 시작 직후 jitterbuffer(50ms)가 처음 지연을 잡는 구간 → 검증: 프레임별 지연 확인 → 확인 (f0~f2 세 프레임에서만 발생)
   - 조치: 전체 및 제외본 전체 보고하는 방향으로 수정.
1. 문제: 원본 비트레이트(약 23Mbps) run에서 지연 p95 62ms
   - 가설 A: 프레임당 패킷 수 증가(약 70개) → 검증: 구간별 지연 분해 → 수정 (증가분이 jitterbuffer+depay 구간에서 나옴)
   - 가설 B: 패킷 손실 → 검증: 수신 패킷 집계 → 확인 (1.32%)
   - 결론: 루프백에서 패킷이 빠진 원인은 미확인. 후보는 UDP 수신 버퍼 크기이며 D03 계획 보고 때 읽기 전용 조회로 확인.
1. 문제: x264enc 출력 PTS에 1000시간 오프셋이 붙음 (GStreamer 1.20)
   - 조치: 송신 측 조인에서 첫 프레임으로 오프셋을 학습하고 meta.json `pts_offset_ns`에 기록
4. 문제: ball 패턴은 원래 비트레이트가 약 200kbps라 목표 500/2000kbps에 못 닿음 (x264 CBR은 filler를 넣지 않음)
   - 조치: `--test-pattern`으로 snow 사용. 실제 클립은 23Mbps라 전제 충족
5. 문제: 원본 비트레이트를 재려고 상한 20000kbps로 60초(d02-clip-native) 돌렸더니 상한에 붙음 (1초 창 중앙값 20260kbps)
   - 가설: 상한이 원본보다 낮아 측정이 잘림 → 검증: 상한 200000kbps로 30초 재측정(d02-clip-native2) → 확인 (중앙값 약 23Mbps)
   - 결론: 원본이 목표 500/2000kbps보다 10배 이상 높아 노브 판정 전제 충족
