## 문제 → 가설 → 검증 → 결론
#### 1. **문제**: 최초 normal run에서 프레임 58개가 "미디코드"로 기록됨 (매칭률 96.83%). 패킷은 19826/19826 도착
   - 가설 A: 디코드 실패 → 검증: `recv_meta.json`의 `decoded_unmapped` = 58, 매핑된 1773 + 58 = 1831 = 송신 프레임 수 → 기각 (디코더는 전부 출력, 수신기의 PTS 매핑이 실패)
   - 가설 B: 네트워크·netem 영향 → 검증: 패킷 손실 0, `RcvbufErrors` 0, normal은 열화 설정 없음 → 기각
   - 가설 C: 송신기 정지 후 몰아 보내기가 PTS 어긋남을 유발 → 검증: 프레임 1110→1111 캡처 간격 1182.7ms, 이후 40프레임이 3~8ms 간격. 매핑 실패 구간(1130~1187)이 정지 직후와 겹침 → 부분 지지 (정상 간격으로 돌아온 뒤에도 37프레임 지속되어 완전한 설명은 아님, 단계별 PTS 미기록)
   - 조치: 수신기에 PTS 진단 기록 추가(`pts_diag`), `match`에 `decoder_outputs`·`unmapped` 표시 추가. 같은 조건으로 `d03-normal-r2` 재실행
   - 결론: r2는 100%, 매핑 실패 0, 정지 재현되지 않음. r2를 normal 기준선으로 채택하고 최초 run은 이상 사례로 보존. 정지 원인은 미확정(후보: 호스트 스케줄링, 디스크 I/O, 클립 소스 일시 정지). 그 시점의 전원·다른 작업: 기억 안남.

#### 2. **문제**: D02에서 23Mbps run의 루프백 패킷 손실 1.32%, 지연 p95 62ms
   - 가설 A: 프레임당 패킷 수 증가 때문 → 검증: 구간별 지연 분해 → 수정 (증가분이 jitterbuffer+depay 구간)
   - 가설 B: 수신 소켓 버퍼 넘침 → 검증: Udp `RcvbufErrors` 0 → 900, `SndbufErrors` 변화 0, 소켓 버퍼 212992(기본값) → 확인
   - 조치: `udpsrc` 버퍼 8MiB 지정(`RTP_RECV_BUFFER_BYTES`), 실제 적용값은 `recv_meta.json`의 `udp_rcvbuf`에 기록(커널이 2배인 16777216 보고). 재측정에서 손실 0
   - 참고: 이전 run은 불완전 프레임이 886/44/0으로, 900개 손실이 44프레임에 몰림 (버퍼 넘침은 몰려서 발생)
#### 3. 문제: 2000kbps에서 프레임당 패킷 10.83개 (예상 약 6개)
   - 가설 A: 비트레이트가 설정보다 높음 → 검증: 실측 2024kbps → 기각
   - 가설 B: `tune=zerolatency`가 프레임을 slice로 나눠 인코딩하고 slice마다 패킷이 최소 하나 → 근거: 최소 8패킷(4KB 미만 프레임 43개 중 42개가 정확히 8패킷), 패킷당 평균 약 779B (MTU 1400의 절반) → 추정 (NAL 파싱으로 확정하지 않음)
   - 의미: 손실률 2%에서 영향받는 프레임 비율이 약 19.7%(1−0.98^10.83)로 계산되고 실측 18.62%와 맞음. slice 수가 CPU 스레드에 의존하면 다른 PC에서 같은 손실률이라도 영향받는 프레임 비율이 달라질 수 있음 (재현성 확인 필요)
-  발견: 패킷 손실이 있어도 디코더가 모든 프레임을 출력하여 fps가 변하지 않음 (세 시나리오 모두 30.04). 열화는 fps가 아니라 지연과 불완전 프레임 비율로 드러남. 손실 run의 jitter_depay p95 49.3ms는 지터버퍼 대기 시간(50ms)과 비슷함 (손실 대기라는 가설, 미검증)
#### 4. 문제: PR #9의 CI(`ci / lint-test`)가 11초 만에 실패. 로컬 `make test`는 100개 통과
   - 로그: `ModuleNotFoundError: No module named 'gi'` (`src/pipe/capture/sender.py:23`, `receiver.py:45`)
   - 수집 결과: `collected 94 items / 3 errors / 8 deselected / 1 skipped / 86 selected`
   - 가설 A: 테스트 로직이 틀렸다 → 검증: 로그 확인 → 기각 (테스트 실행 전 수집 단계에서 import 오류, 실패한 파일 3개가 모두 같은 원인)
   - 가설 B: 환경 준비(의존성 설치, 락 파일) 단계 문제 → 검증: 실패 시간 11초와 로그의 단계 확인 → 기각 (설치는 통과, `make test` 단계에서 실패)
   - 가설 C: 새 테스트 3개가 `gi`가 필요한 모듈(`sender`, `receiver`)에서 순수 함수를 import하고, CI는 `gst` 그룹 없이 기본 그룹만 설치한다 → 검증: `sys.modules['gi'] = None`으로 막은 상태에서 단위 테스트 실행 → 확인 (수정 전 같은 수집 오류 3건 재현, 종료 코드 2)
   - 로컬에서 안 보인 이유: 로컬 venv에는 `gst` 그룹이 설치돼 있었음
   - 조치: `gi`와 무관한 함수를 `recv_diag.py`(receiver의 상수·함수·`CappedLog`)와 `config.py`(`apply_overrides`)로 이동. 함수 본문은 수정하지 않음. 테스트 3개는 import 경로만 변경
   - 재발 방지: `gi`를 막은 하위 프로세스에서 `pytest --collect-only`를 실행하는 가드 테스트 추가. 이제 로컬 `make test`에서도 같은 실수를 잡음
   - 검증: `gi` 차단 상태 101개 통과, `make test` 101개 통과, `make lint` 통과, 통합 테스트 4개 통과, `sender`·`receiver --help` 출력 해시 수정 전후 동일
   - CI 재실행 결과: - `make test` 100개 통과, `make lint` 통과 / netns 통합 테스트는 sudo가 필요해서 CI에서 제외
   - 커밋: `cff145a`

## 결정 기록
- 결정: 순수 함수를 `gi` 없는 모듈로 분리 / 제친 대안: (A) `gi` import 지연 (`receiver`가 import 시점에 `sender`의 `Gst`를 복사해 가는 구조라 전역 재바인딩 코드가 필요하고 동작이 바뀔 위험이 큼), (C) `importorskip("gi")`로 CI에서 건너뜀 (CI에서 검증이 사라짐), (D) CI에 PyGObject 설치 (CI가 무거워지고 "CI는 기본 그룹만"이라는 기존 결정과 충돌) / ADR: 없음 (되돌리기 쉬운 코드 구조 변경)

## 결정 기록
- 결정: 시나리오 YAML은 항상 구간 리스트 / 제친 대안: 평면형, base+timeline (형식 통일과 실행 경로 단일화, 덮어쓰기 규칙이 숨은 버그 위험) / ADR: 없음
- 결정: 시계열 프로파일은 계단식 구간 / 제친 대안: 키프레임+선형 보간 (1초마다 tc 호출, replace 시 큐 영향 미측정). cell_edge run은 D03에서 하지 않음
- 결정: 지터는 재정렬 허용, rate는 `netem rate` (tbf 제침). 방향은 ue→edge만 (D22 제어 명령·ack 전에 반대 방향 추가)
- 결정: link.metrics는 D03에서 overview 필드 기준 JSONL로 기록, pydantic 모델화는 D05 / 제친 대안: D03에서 모델 선도입 (D05 범위 선취). 필드명에 단위 접미사(`delay_ms`, `jitter_ms`, `loss_pct`, `rate_kbps`), overview와 차이는 D05에서 계약 문서와 정리. `tc`의 `kbps`는 킬로바이트/초라 변환기는 항상 `kbit`를 쓰고 단위 테스트로 보장
- 결정: 프레임 분류는 완전 / 불완전 / 손실. 매칭률 = 디코드 출력이 있는 비율, 불완전 비율은 별도. 한계: 패킷이 모두 도착해도 앞 프레임 손실로 화면이 깨진 프레임은 완전으로 분류됨
- 결정: 수신 버퍼 기본 8MiB, GST 디버그 로그는 수신기 전용에 20MB 상한
- 결정: sudo는 내 터미널에서 직접 실행. NOPASSWD 등록은 거부 (`ip netns exec`가 임의 명령을 root로 실행할 수 있어 사실상 root 전체 개방)
- 결정: PTS 매핑 방식 변경((a) 유지 / (b) 순서 기반 큐 / (c) 버퍼 메타데이터)은 보류. 근거 사례가 최초 normal 하나뿐. D06에서 추론 결과가 rtp_ts를 들고 가야 하므로 그때 재검토
- 결정: 정상 기준선은 r2 / ADR: 없음 (ADR-0002의 "감수하는 점"과 같은 계열이라 재검토 조건 확인)
