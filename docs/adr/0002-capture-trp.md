# ADR-0002: 프레임 식별 방식
- 상태: 제안 | 날짜: 2026-11-02

## 배경
- 송신한 프레임과 수신해서 디코드한 프레임을 같은 프레임으로 짝지어야 한다.
  지연, 손실, 감지 지연 지표가 모두 이 짝짓기에 의존한다.
- 제약 조건
  - 송신 중 해상도·fps·비트레이트가 바뀐다(적응 정책).
  - D03부터 링크에서 지연·지터·손실이 생긴다.
  - 식별자가 추론 단계까지 이어져야 한다.
  - 송신은 H.264 x264enc RTP/UDP, 환경은 GStreamer 1.20.3이다.

## 선택지
- A. RTP 타임스탬프 매칭: 표준 RTP 헤더의 ts를 키로 쓴다. 조인 키는 (ssrc, rtp_ts).
- B1. RTP 헤더 확장에 seq 또는 시각을 삽입한다.
- B2. H.264 SEI(user_data_unregistered)에 seq를 삽입한다.
- B3. 영상 안에 프레임 번호 바코드(워터마크)를 넣는다.

| 기준            | A                                                             | B1                                              | B2                                            | B3                        |
| ------------- | ------------------------------------------------------------- | ----------------------------------------------- | --------------------------------------------- | ------------------------- |
| 손실·재정렬 내성     | 미측정(D03). 재정렬은 jitterbuffer가 처리, 프레임이 통째로 안 오면 손실로 집계         | 미측정. 패킷 단위로 식별자를 읽을 수 있음                        | 미측정. 프레임이 디코드되면 식별 가능                         | 미측정. 압축 열화로 판독 실패 가능      |
| 해상도·fps 전환 내성 | 실측 통과: 320x240@15 전환 중 키 충돌 없음, 매칭률 100%                      | 미측정. 패킷 계층이라 무관할 것으로 추정                         | 미측정. 인코더 재초기화 후 삽입이 유지되는지 확인 필요               | 미측정. 해상도를 낮추면 판독 실패 위험    |

### 선택지별 정리
- A
  - 장점: 영상과 RTP를 바꾸지 않는다. D02에서 이미 동작한다.
  - 단점
    - 송신 측 메타(`frame.sent`)가 따로 전달되어야 조인할 수 있다.
    - 재시작하면 ssrc와 ts 오프셋이 바뀌어 `(ssrc, rtp_ts)` 키가 필요하다.
    - 송신 측 조인이 x264enc의 출력 PTS 오프셋(1000시간)에 의존한다.
      첫 프레임으로 학습하는 방식이라 인코더 동작이 바뀌면 영향을 받는다.
- B1: capture 시각을 패킷에 직접 실을 수 있다. 헤더 확장 협상과 구현 복잡도가 있고, 디코드 후에는 사라진다.
- B2: 녹화나 전달을 거쳐도 남는다. 구현 위험이 크고 파서·버전에 의존한다.
- B3: 끝단 대 끝단으로 확실하다. 이 프로젝트에서는 화면을 오염시키는 점이 문제다.
  - 추론 입력이 달라진다.
  - 원본 클립 기준 정답(기준 모델 추론)과 수신 영상이 달라진다.

### 실측 사실 (D02)
- 클립 60초 송수신: 송신 1831, 매칭 1831, 매칭률 100%, 손실 0
- 비트레이트·해상도·fps 변경 중에도 ssrc 1개, 키 충돌 없음, 매칭률 100%
- 지연(루프백): 평균 5.21ms, p95 6.97ms
- `rtphdrextntp64`는 GStreamer 1.20.3에 없음

(표의 "손실·재정렬 내성" 행, A 열을 아래로 교체)
미측정(D03). 재정렬은 jitterbuffer가 처리. 프레임이 통째로 안 오면 손실로 집계.
D02에서 루프백 패킷 손실 1.32%(23Mbps run)가 나왔고, 일부 패킷이 빠진 프레임도
디코드되는 경우가 보고됨. 불완전 프레임을 손실로 셀지는 미정.

## 결정
A(RTP 타임스탬프 매칭)로 진행한다.

- 결정적 기준은 해상도·fps 전환 내성과 구현 비용이다. 이 프로젝트는 송신 중
  해상도·fps·비트레이트를 바꾸는 적응 정책이 핵심이다. A는 D02에서 전환 중에도
  키 충돌 없이 매칭률 100%였고 이미 구현되어 있다.
- B1은 GStreamer 1.20.3에 `rtphdrextntp64`가 없어 직접 구현해야 하고, 디코드 후에는
  사라져 A와 같은 매핑이 필요하다. 구현 비용만 늘고 얻는 것이 적다.
- B2는 x264enc가 SEI 삽입을 직접 지원하지 않아 비트스트림을 가공해야 한다.
  구현 위험이 크다.
- B3은 영상을 변조한다. 추론 입력이 바뀌고, 원본 클립 기준 정답(기준 모델 추론)과
  수신 영상이 달라져 비교 지표가 오염된다.
- 의심한 점은 손실·재정렬에서 깨질 가능성이다. D02는 루프백이라 검증하지 못했다.
  D03 netem 시나리오에서 확인하고, 깨지면 재검토한다.

## 감수하는 점
- 송신 측 메타(`frame.sent`)가 따로 전달되어야 조인할 수 있다.
- 송신이 재시작되면 ssrc와 ts 오프셋이 바뀐다. 조인 키는 `(ssrc, rtp_ts)`로 둔다.
- 송신 측 조인이 x264enc 출력 PTS 오프셋(1000시간)에 의존한다. 첫 프레임으로
  오프셋을 학습하고 `meta.json`의 `pts_offset_ns`에 기록한다. 인코더 동작이 바뀌면
  조인이 틀어질 수 있다.
- 추론 단계로는 rtp_ts를 따로 들고 가야 한다.
- 지연은 이 선택의 위험이 아니다. A는 영상과 RTP를 바꾸지 않아 지연을 늘리지 않는다.

## 다시 검토할 조건
- D03 netem 손실·재정렬 시나리오에서 오매칭(잘못된 짝)이 1건이라도 생기거나,
  수신 측에만 있는 레코드가 생긴 경우
- 송신 재시작 후 `(ssrc, rtp_ts)` 키가 충돌한 경우
- PTS 오프셋 학습이 실패하거나 인코더 동작 변경으로 조인이 어긋난 경우
- 손실이 없는 구간에서 매칭률이 100% 아래로 떨어진 경우
- 실제 IP 카메라를 쓸 때 ts 규칙이 달라 매칭이 안 되는 경우
